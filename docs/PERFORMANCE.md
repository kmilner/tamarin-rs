# Performance

[Back to README](../README.md)

Commands below run from the repository root.

Both provers ran all lemmas on eight representative theories with
`--derivcheck-timeout=30` on a 16-core Apple silicon Mac using Maude 3.5.1.
Haskell used `+RTS -N{1,4,16}` and Rust (`ea11e08`) used
`--processors={1,4,16}`. The Haskell baseline is the **tamarin-prover 1.12.0
release**. The develop branch this repo pins for parity testing carries
performance work of its own that is not in a release yet, so expect a
smaller gap against a develop build. Tables are generated by
`scripts/bench.sh` (regenerate in place with `scripts/bench.sh --write`);
the RS+HS and RS columns show the change versus Haskell (negative = faster
/ less memory).

**Reading the tables:** HS is the Haskell prover; RS is the Rust port. RS+HS
measures proving with Rust and then rechecking the emitted proof with Haskell
using `prove_and_reverify.sh`. Each cell is a single run; wall-clock timings
are noisy by about ±10%. Peak memory is the largest simultaneous RSS sum
across the full process tree, including Maude workers, sampled every 20 ms.
For RS+HS, peak memory is the larger peak of the two phases.

Across all theories and core counts the Rust port is
3.4–100× faster than the 1.12.0 release (median 25×). On one core Rust
uses 66–97% less peak memory. On sixteen cores Rust uses 36% less peak
memory on `NSPK3` (130 vs 203 MB) and 93% less on `CCITT_X509_3`
(770 vs 11,672 MB). The smallest speed gains are on `Joux`, whose runtime
is dominated by AC-heavy Maude queries both provers pay for equally.

The `not supported` entries in the RS+HS column are not failures of the
port: the emitted `Joux` and `wireguard` proofs are correct, but the
unpatched 1.12.0 release cannot replay them (`analysis incomplete`) due
to two upstream tamarin-prover issues —
[#871](https://github.com/tamarin-prover/tamarin-prover/issues/871)
(proof shape depends on thread count; already fixed on the develop
branch) and
[#881](https://github.com/tamarin-prover/tamarin-prover/issues/881)
(emitted proofs normalise differently on reload; fix pending in
[#882](https://github.com/tamarin-prover/tamarin-prover/pull/882)). The
patched `./setup.sh testing` build includes both fixes and re-verifies
both theories.

The port parallelises at two levels, both via rayon: independent lemmas are
proved concurrently, and within a lemma the proof-search fan-out and source
saturation run in parallel over a pool of Maude subprocesses
(`--processors=N` sets the worker count, `--maude-processes=M`, default `N`,
the pool size). Multi-lemma theories gain the most across cores; theories
dominated by source saturation also speed up at a single core because
refined sources are computed once and shared across lemmas.

## Memory limits

On Linux and macOS, `--memory-limit=<size>` monitors the combined memory of a
batch run, including Maude and other helpers. It measures RSS on Linux and
physical footprint on macOS. The macOS metric includes compressed memory and
excludes pages marked reusable, even when those pages remain resident:

```bash
tamarin-rs --memory-limit=4GiB --prove theory.spthy
```

`+RTS -M4G -RTS` is equivalent. Sizes accept bytes or binary K/M/G/T suffixes
(case-insensitive), also spelled KiB/MiB/GiB/TiB. Decimal quantities such as
`1.5G` work; `0` disables the limit. The last native or RTS memory setting wins.
Unlike GHC's `-M`, this measures the prover and helpers, not just the language heap.

Exceeding the threshold stops the job and exits **251**, matching GHC heap
exhaustion. Unfinished proofs are lost. This is an approximate limit: usage
can overshoot, shared pages can be counted more than once, and detached helpers
or unavailable process data may be missed. Linux RSS excludes swapped-out memory.
On macOS, a footprint query failure stops the job with an error unless the
sampled process has already exited.
Reducing `--maude-processes` also reduces baseline memory use.
